# v4 licensing architecture

`LICENSE_MATRIX.toml` is the ordered path authority. Licensing and product
capability classification are independent: public trust-core/runtime code and
public SDK/protocol schemas remain Apache-2.0, while only explicitly mapped
new commercial source paths can use the custom `LicenseRef` draft.

The root `LICENSE`, `NOTICE`, and `CLA.md` are historical artifacts and are
not edited by this phase. `LICENSES/Apache-2.0.txt` is an exact byte copy of
the baseline Apache artifact. `legal/cla/CLA-v1-legacy.md` is an exact,
digest-pinned copy of the baseline `CLA.md`. These facts preserve v3 grants;
they do not create a retroactive dual-license or change existing signatures.

`legal/cla/CLA-v2.md` is a versioned candidate derived from the current CLA
text, with explicit provenance. It is NON-OPERATIVE and PENDING COUNSEL; v1
signatures cannot be treated as v2 acceptance. A separate signature store and
external approval are required before any v2 workflow or release claim.

The frozen v1 signature evidence is read-only external history at commit
`f09ea6d8a28066007678342056ac8be95df756d7`, path
`signatures/v1/cla.json`, SHA-256
`831846e0db4c8d1d097eb8988e23685bb5990030641c8b6c9f5cae83ced6a56e`, with 19
signers. The former 18-signer pin is stale and rejected; this slice does not
create or claim a v2 signature source.

`private_service` paths are forbidden in the public tree. `commercial` paths
need an SPDX header and auditable post-boundary provenance. `generated` and
`third_party` paths declare generator/upstream ownership and notice evidence.
Ambiguous, unclassified, traversal, or symlinked tracked paths fail the audit.

`THIRD_PARTY_NOTICES` is generated by `scripts/generate-third-party-notices.py`.
The generator is hermetic: it runs `cargo metadata --locked --offline
--all-features`, verifies the exact `rust/Cargo.lock` digest, checks
`SBOM.cdx.json`, and validates `legal/third-party-assets.toml` against every
shipped dashboard, font, vendored rmcp, and npm SDK artifact. It never fetches
network data and never writes legal approval evidence.

Use the following workflow after any dependency or asset change:

    python3 scripts/generate-third-party-notices.py --root . --write
    python3 scripts/generate-third-party-notices.py --root . --check
    python3 scripts/ip-provenance-audit.py --root .

`--check` is invoked by the existing provenance audit path in CI and release.
It accepts only byte-identical pending or approved generated output. Normal
audit reports `GENERATED - PENDING APPROVAL` as a warning; release-strict
requires `Status: GENERATED AND APPROVED` plus
`legal/third-party-notices-approval.toml` with exactly one non-empty approver
(`approving_counsel` or, since 2026-09-28, `approving_owner` for approval by
the copyright owner), `approval_evidence`, `approved_at`, and
`approved_content_sha256` equal to the SHA-256 of the exact notice bytes.
Generation cannot create or update that approval file.

The commercial license and trademark policy are drafts, not legal advice and
not operative grants. `LEGAL_REVIEW_REQUIRED.md` is the release-blocking
decision checklist. Branch protection, counsel approval, and signature-store
setup are external actions and cannot be claimed from repository code.

The reproducible current classification and authorship findings are recorded
in the private IP-provenance report (not published). It explicitly records that this
candidate moves no executable Apache source into a commercial class.
